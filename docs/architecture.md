# Архитектура и механика доставки

Документ описывает, как устроен процесс доставки: что происходит от коммита до трафика
на новой версии, и почему принятые решения именно такие.

## Путь коммита до продакшена

```
  push / pull request
          │
          ▼
  ┌───────────────────────────────────────────────┐
  │ CI (.github/workflows/ci.yml)                  │
  │                                                │
  │  lint  unit  integration  sast  sca            │
  │  secrets  policy  helm                         │  все параллельно
  │                     │                          │
  │                     ▼  needs: все восемь       │
  │  build: сборка → скан Trivy → push в GHCR      │
  └──────────────────────┬────────────────────────┘
                         │  только для main
                         ▼
  ┌───────────────────────────────────────────────┐
  │ CD (.github/workflows/cd.yml)                  │
  │                                                │
  │  kind → RBAC → секреты → kubeconfig от SA      │
  │  PostgreSQL → Prometheus/Grafana               │
  │  deploy.sh на каждый сервис (blue-green)       │
  └───────────────────────────────────────────────┘
```

CI запускается на push в `main` и `development` и на каждый pull request в `main`.
CD подписан на успешное завершение CI **только на `main`**, поэтому деплой происходит
по факту влитого pull request, а не на каждый коммит в рабочей ветке.

## Почему скан образа стоит до пуша

Требование этапа B звучит как "запретить пуш при критических уязвимостях". Очевидная
реализация - собрать, запушить, потом просканировать - выполняет его лишь формально:
уязвимый образ уже лежит в реестре и его можно случайно развернуть.

Поэтому джоб `build` собирает образ в локальный демон раннера (`load: true`), сканирует
его, и выполняет `docker push` только если скан чист. В реестр физически не попадает
образ, который не прошёл проверку.

Это не умозрительная предосторожность. На одном из прогонов гейт остановил все три образа:

| Образ | Находка | Источник |
|---|---|---|
| auth-service, orders-service | CVE-2026-59873, `tar` 7.5.11 | npm внутри базового `node:22-alpine` |
| web-client | CVE-2026-31789, OpenSSL 3.3.3-r0 | устаревший Alpine в `nginx-unprivileged:1.27` |

Ни одна не была в коде проекта. Исправления - удаление npm из runtime-слоя (в рантайме
выполняется `node src/server.js`, npm не нужен) и обновление базового образа nginx.
Ни `.trivyignore`, ни снижение порога до HIGH не использовались.

## Blue-green: механика переключения

### Состояние в кластере

Чарт [microservice](../infra/helm/microservice/) рендерит для каждого сервиса:

- `<service>-blue` и `<service>-green` - два Deployment
- `<service>` - Service с селектором `color: {{ .Values.activeColor }}`
- `<service>-preview` - Service с селектором на противоположный цвет

Активный цвет не хранится в файлах - он читается из живого кластера:

```bash
kubectl -n lab get svc orders-service -o jsonpath='{.spec.selector.color}'
```

Это делает пайплайн идемпотентным и не требует внешнего хранилища состояния.

### Почему у каждого цвета свой тег

Ключевое решение чарта: `colors.blue.tag` и `colors.green.tag` задаются раздельно.

Если бы тег был один на весь релиз, `helm upgrade` с новым тегом переписал бы оба
Deployment, работающий цвет пересоздался бы вместе с новым, и никакой безопасности
выката не осталось бы - обе версии стали бы новыми одновременно.

Поэтому [deploy.sh](../infra/scripts/deploy.sh) перед выкатом читает тег активного цвета
из кластера и передаёт его обратно без изменений:

```bash
ACTIVE_TAG="$(tag_of_color "$ACTIVE")"
release_service "$ACTIVE" "$ACTIVE_TAG" "$TAG" true true
```

Работающая версия остаётся нетронутой, пока проверяется новая.

### Последовательность выката

1. прочитать активный цвет; если Service нет - это первый релиз, выкатывается blue
2. `helm upgrade --atomic` поднимает противоположный цвет с новым тегом,
   `activeColor` остаётся прежним, трафик не двигается
3. `kubectl rollout status` ждёт готовности нового цвета
4. [run-e2e.sh](../infra/scripts/run-e2e.sh) пробрасывает порты и гоняет сценарий
   **через preview Service**, то есть против новой версии без пользователей
5. при успехе - `helm upgrade` с новым `activeColor`, трафик переключается атомарно
6. при провале - новый цвет выключается, `activeColor` не меняется

Старый цвет после переключения остаётся запущенным. Это осознанно: откат сводится к
обратной смене селектора и занимает секунды, без пересборки и повторного выката.

### Три уровня отката

**Уровень 1, `helm upgrade --atomic`.** Если поды нового цвета не проходят readiness за
таймаут, Helm сам возвращает релиз к предыдущему состоянию. Ловит поломки, которые видны
сразу: невалидный конфиг, отсутствующий секрет, падение процесса на старте.

**Уровень 2, провал e2e против preview.** Ловит поломки, которые видны только под
нагрузкой сценария: сломанная бизнес-логика, несовместимость с базой, ошибка авторизации.
Пользовательский трафик при этом вообще не участвует - он всё время на старом цвете.

**Уровень 3, [rollback.sh](../infra/scripts/rollback.sh).** Для случая, когда переключение
уже произошло, а проблема обнаружилась позже. Возвращает селектор на прежний цвет;
если `helm upgrade` не проходит, используется `helm rollback` на предыдущую ревизию.

Проверить второй уровень можно воспроизводимо: запуск CD через `workflow_dispatch` с
галкой `fail_mode` выставляет `FAIL_MODE=1` в секрете, из-за чего новые поды orders-service
отвечают 500 на `/orders`. Пайплайн фиксирует цвет до и после и падает, если трафик
всё-таки ушёл на сломанную версию.

Важная деталь: патч секрета влияет только на **новые** поды, потому что переменные
читаются при старте контейнера. Поды работающего цвета не пересоздаются и продолжают
обслуживать запросы - именно это и требуется продемонстрировать.

## Миграции и порядок выката

Миграции выполняются Job с аннотациями Helm:

```yaml
helm.sh/hook: pre-install,pre-upgrade
helm.sh/hook-weight: "-5"
helm.sh/hook-delete-policy: before-hook-creation
```

Helm дожидается завершения hook до создания подов, поэтому схема гарантированно
актуальна к моменту старта нового кода. Провал миграции останавливает релиз целиком,
не оставляя приложение на несовместимой схеме.

Job запускается тем же образом, что и сервис, но с командой `node src/migrate.js` -
отдельный образ для миграций не нужен, а версия кода и версия схемы приезжают вместе.

Раннер [migrate.js](../orders-service/src/migrate.js) ведёт таблицу `schema_migrations`,
применяет только неприменённые файлы и оборачивает каждый в транзакцию. Повторный запуск
на актуальной схеме ничего не делает - это проверяется интеграционным тестом.

При откате миграции **не отменяются**: `rollback.sh` передаёт `migrations.enabled=false`.
Обратные миграции требуют совместимости схемы с обеими версиями кода, что выходит за
рамки этой работы; здесь достаточно того, что схема меняется только вперёд и только
совместимым образом (вторая миграция добавляет колонку со значением по умолчанию).

## Минимальные права CI/CD

[rbac.yaml](../infra/k8s/rbac.yaml) описывает ServiceAccount с Role, ограниченной одним
namespace: без ClusterRole, без прав на nodes и на другие namespace.

Само по себе наличие такого файла ничего не доказывает - деплой мог бы идти под admin.
Поэтому CD собирает отдельный kubeconfig из токена этого ServiceAccount:

```bash
token="$(kubectl -n lab get secret cicd-deployer-token -o jsonpath='{.data.token}' | base64 -d)"
kubectl config --kubeconfig=/tmp/deployer.kubeconfig set-credentials cicd-deployer --token="$token"
```

и все последующие вызовы `helm` и `kubectl` идут через него. Отдельный шаг печатает
результат `kubectl auth can-i` в summary и **валит пайплайн**, если деплойер вдруг
получит доступ к nodes. Права проверяются, а не декларируются.

Право `pods/portforward` выдано намеренно: без него нельзя достучаться до preview Service
и прогнать e2e до переключения трафика.

### Почему RBAC Prometheus вынесен из чарта

Первый запуск CD упал именно на этом ограничении:

```
serviceaccounts "prometheus" is forbidden:
User "system:serviceaccount:lab:cicd-deployer" cannot get resource "serviceaccounts"
```

Чарт monitoring пытался создать ServiceAccount и Role для Prometheus, а у деплойера таких
прав нет. Соблазн выдать их надо было отклонить: аккаунт, способный создавать Role и
RoleBinding, может выписать себе любые привилегии, и вся конструкция least privilege
перестала бы что-либо значить.

Поэтому RBAC-объекты Prometheus вынесены в [monitoring-rbac.yaml](../infra/k8s/monitoring-rbac.yaml)
и применяются администратором кластера вместе с namespace, до переключения на
ограниченный kubeconfig. Чарт только ссылается на ServiceAccount по имени.

Это общее правило разделения: администратор раздаёт права, CI/CD ими пользуется и
не может их расширить.

## Наблюдаемость

Оба Node-сервиса отдают `/metrics` через `@prometheus-io/client`: метрики процесса плюс
`http_requests_total{method,route,status}` и гистограмма `http_request_duration_seconds`.

Prometheus находит поды через `kubernetes_sd_configs` по аннотации `prometheus.io/scrape`,
которую чарт проставляет автоматически. В метки переносятся `app` и `color` из лейблов
пода - благодаря этому дашборд умеет разделять данные по цветам.

Панель "Scraped pods by colour" на [дашборде](../infra/helm/monitoring/dashboards/lab.json)
показывает `sum(up) by (service, color)`. На ней видно, как во время выката появляется
второй цвет, а после переключения трафик обслуживает уже он. Это самый наглядный способ
показать blue-green на защите.

При падении CD собирает логи всех подов, `describe` и события кластера в артефакт
workflow. Кластер kind эфемерный и уничтожается вместе с раннером, поэтому без такого
шага разобрать упавший деплой было бы нечем.

## Принятые ограничения

| Решение | Обоснование |
|---|---|
| kind вместо облачного кластера | задание требует деплой в Kubernetes, не оговаривая провайдера; kind - настоящий Kubernetes, воспроизводимый и бесплатный |
| один чарт `microservice` вместо трёх | три копии одинаковой blue-green логики разъехались бы при первой правке |
| `kubectl logs` вместо Loki | задание прямо допускает такой вариант; Loki в эфемерном кластере избыточен |
| Kubernetes Secrets вместо Vault | задание допускает оба; Vault потребовал бы отдельного развёртывания и unseal-процедуры |
| откат без обратных миграций | требует совместимости схемы с двумя версиями кода одновременно, что выходит за рамки работы |
| анонимный просмотр в Grafana | нужен для скриншотов; права ограничены ролью Viewer, пароль администратора живёт в секрете |
