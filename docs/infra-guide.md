# Инфраструктура: подробный разбор

Что лежит в `infra/`, зачем каждый файл и как устроена сборка метрик.

---

## Карта каталога

```
infra/
├── kind-config.yaml        описание локального кластера
├── k8s/                    манифесты, применяемые напрямую через kubectl
│   ├── namespace.yaml
│   ├── rbac.yaml               права для CI/CD
│   └── monitoring-rbac.yaml    права для Prometheus
├── helm/                   пакеты Helm
│   ├── microservice/           один чарт на все три сервиса
│   ├── values/                 различия между сервисами
│   ├── postgresql/             база данных
│   └── monitoring/             Prometheus и Grafana
└── scripts/                скрипты развёртывания
```

Разделение на `k8s/` и `helm/` не случайно: в `k8s/` лежит то, что создаётся
**один раз администратором**, в `helm/` - то, что переустанавливается при каждом
релизе.

---

## Кто за что отвечает

Частое заблуждение - что Helm как-то участвует в сборке образов. Это не так,
инструменты не пересекаются:

| Инструмент | Зона ответственности |
|---|---|
| **Docker** | собирает образ из Dockerfile |
| **GHCR** (реестр) | хранит собранные образы |
| **Helm** | описывает, **как запускать** уже готовые образы |
| **Kubernetes** | собственно запускает и следит |
| **скрипты в `scripts/`** | связывают всё это в процесс выката |

Helm никогда не притрагивается к образам. Он генерирует YAML-манифесты, где имя
образа записано обычной строкой:

```yaml
image: "ghcr.io/ivanribin/orders-service:sha-42af804"
```

Kubernetes читает эту строку и сам идёт в реестр.

**Аналогия.** Образ - коробка с программой. Чарт - инструкция по установке: куда
ставить, сколько копий, какие настройки, как проверять здоровье. Kubernetes -
тот, кто выполняет инструкцию. В инструкции нет самой программы, только ссылка.

### Что даёт Helm

Без него пришлось бы писать голые манифесты руками: шесть почти одинаковых файлов
(три сервиса на два цвета), с ручной правкой тега при каждом релизе и без всякой
истории версий.

| Возможность Helm | Что даёт у нас |
|---|---|
| шаблоны | один чарт вместо трёх копий |
| релизы с ревизиями | `helm rollback` возвращает предыдущую версию |
| хуки | миграции выполняются до старта подов автоматически |

### Что даёт папка scripts

Helm **не умеет blue-green**. Он умеет установить чарт и откатить релиз, но не
знает, что значит «определить активный цвет, выкатить противоположный, проверить
тестами и только потом переключить трафик».

Эта логика написана в скриптах: `kubectl` спрашивает состояние кластера, `helm`
его меняет, `node` проверяет результат. Скрипт задаёт порядок.

### Три папки одной строкой

```
k8s/      в каких границах и с какими правами   (применяет администратор)
helm/     что и как запускать                   (шаблоны манифестов)
scripts/  в каком порядке и с какими проверками (сценарий выката)
```

## kind-config.yaml

Описывает локальный кластер. Главное в нём - проброс портов из кластера на твою
машину:

| Внутри кластера | На хосте | Что становится доступно |
|---|---|---|
| 30080 | 8080 | приложение |
| 30300 | 3000 | Grafana |
| 30900 | 9090 | Prometheus |

Без этого блока кластер работал бы, но достучаться до него из браузера было бы
нельзя. В CD этот проброс не нужен - там никто не открывает браузер.

---

## k8s/rbac.yaml - права для CI/CD

Создаёт `ServiceAccount` с именем `cicd-deployer` и выдаёт ему права **только в
namespace `lab`** и только на нужные типы объектов: поды, сервисы, деплойменты,
секреты, джобы, конфигмапы.

Чего у него **нет**: доступа к узлам кластера, к другим namespace, к созданию
ролей.

В CD пайплайн собирает из токена этого аккаунта отдельный kubeconfig и все
команды выполняет от его имени. Отдельный шаг проверяет это через `kubectl auth
can-i` и валит сборку, если прав оказалось больше положенного.

## k8s/monitoring-rbac.yaml - права для Prometheus

Prometheus должен видеть список подов, чтобы находить, с кого собирать метрики.
Для этого ему нужен свой ServiceAccount с правом читать поды.

**Почему этот файл вынесен из чарта.** Чарт устанавливается от имени
`cicd-deployer`, а у него намеренно нет прав создавать роли. Причина простая:
аккаунт, способный создавать роли, может выдать сам себе любые права - и вся
идея минимальных привилегий теряет смысл. Поэтому роли для Prometheus применяет
администратор один раз, а чарт только ссылается на готовый ServiceAccount по
имени.

Это пример того, как ограничение прав влияет на структуру проекта.

## Чарт microservice - blue-green

Один чарт обслуживает все три сервиса. Различия вынесены в `helm/values/`.

### Как рождаются два цвета

В `values.yaml` есть блок:

```yaml
colors:
  blue:
    enabled: true
    tag: ""
  green:
    enabled: false
    tag: ""
```

Шаблон `deployment.yaml` проходит по этому списку циклом и создаёт по одному
Deployment на каждый **включённый** цвет. Поды получают метку `color: blue` или
`color: green`.

**У каждого цвета свой тег образа.** Это ключевая деталь: во время выката старая
версия продолжает работать на старом образе, новая поднимается на новом. Если бы
тег был общий, Helm пересоздал бы оба Deployment сразу, и безопасного выката не
получилось бы.

### Два Service

`service.yaml` создаёт два объекта:

| Service | Селектор | Кто им пользуется |
|---|---|---|
| `orders-service` | `color: <активный>` | пользователи |
| `orders-service-preview` | `color: <неактивный>` | только тесты в пайплайне |

Переключение трафика - это изменение **одного поля** `activeColor`, после чего
основной Service начинает направлять запросы на поды другого цвета. Мгновенно и
без промежуточных состояний.

### Job миграций

`migration-job.yaml` создаёт Job с аннотацией:

```yaml
helm.sh/hook: pre-install,pre-upgrade
```

Helm выполняет такой Job **до** создания подов и ждёт его завершения. Если
миграция упала - релиз останавливается, и новый код не запустится на старой
схеме базы.

### Запрет тега latest

В `_helpers.tpl` есть функция, которая вызывает `fail`, если тег пустой или равен
`latest`. Проверка срабатывает при рендеринге шаблона, то есть релиз просто не
соберётся. Это защита от ручного `helm install` мимо пайплайна.

## Blue-green и откат: полный разбор

### Задача, которую решает стратегия

При обновлении приложения есть момент, когда новая версия уже принимает запросы,
но ещё не проверена в реальных условиях. Если в ней ошибка - её увидят
пользователи. Стратегия выката определяет, как сократить или убрать этот момент.

### Три подхода

| Стратегия | Как работает | Слабое место |
|---|---|---|
| **Rolling update** (по умолчанию в Kubernetes) | поды заменяются по одному | во время выката часть трафика уже идёт на новую версию |
| **Canary** | новая версия получает 5%, потом 20%, потом всё | часть пользователей всё равно видит сломанную версию |
| **Blue-green** | новая версия поднимается полностью, но без трафика; переключение мгновенное | нужно держать две версии одновременно, то есть вдвое больше ресурсов |

Мы выбрали blue-green: при нём **не существует состояния**, когда часть
пользователей на непроверенной версии. Трафик либо весь на старой, либо весь на
новой.

### Как это выглядит у нас

Два Deployment с метками `color: blue` и `color: green` и два Service:

```
                  ┌─────────────────────┐
пользователи ────>│ Service             │  селектор: color = blue
                  │ orders-service      │
                  └──────────┬──────────┘
                             ▼
                      ┌─────────────┐        ┌──────────────┐
                      │ blue        │        │ green        │
                      │ версия v1   │        │ выключен     │
                      │ 2 пода      │        │              │
                      └─────────────┘        └──────────────┘
                                                    ▲
                  ┌─────────────────────┐           │
    только  ─────>│ Service             │───────────┘
    тесты         │ orders-svc-preview  │  селектор: color = green
                  └─────────────────────┘
```

Переключение трафика - это изменение **одного поля** в основном Service:
`color: blue` меняется на `color: green`. Kubernetes сразу начинает направлять
запросы на другие поды.

### Полный цикл выката, шаг за шагом

**Состояние до выката**

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1 | весь |
| green | выключен | нет |

**Шаг 1. Определить активный цвет**

```bash
kubectl get svc orders-service -o jsonpath='{.spec.selector.color}'
```

Скрипт читает это прямо из кластера, а не хранит где-то у себя. Получает `blue`,
значит цель - `green`.

**Шаг 2. Узнать тег работающей версии**

```bash
kubectl get deploy orders-service-blue -o jsonpath='{...containers[0].image}'
```

Нужно, чтобы при следующем шаге **не тронуть работающий цвет**. Helm перезапишет
весь релиз целиком, поэтому старый тег надо передать обратно без изменений.

**Шаг 3. Выкатить новый цвет**

```
helm upgrade --install orders-service ... \
  --set activeColor=blue          ← трафик остаётся на старом
  --set colors.blue.tag=v1        ← старая версия не меняется
  --set colors.green.enabled=true ← поднимаем новую
  --set colors.green.tag=v2
  --atomic
```

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1 | весь |
| green | v2, поднимается | **нет** |

Флаг `--atomic` - первый предохранитель: если поды green не пройдут readiness за
отведённое время, Helm сам вернёт релиз в предыдущее состояние.

**Шаг 4. Дождаться готовности**

```bash
kubectl rollout status deploy/orders-service-green
```

Готовность определяется readiness probe. Для orders-service она делает `SELECT 1`
к базе, то есть под считается готовым, только если реально может работать.

**Шаг 5. Проверить новую версию тестами**

E2E запускаются **через preview Service**, который ведёт на green:

```
[e2e] auth=auth-service orders=orders-service-preview web=web-client
```

Обрати внимание: auth и web берутся через обычные Service, а orders - через
preview. Проверяется именно та версия, которую собираются выкатить.

**Шаг 6a. Тесты прошли - переключаем**

```
helm upgrade ... --set activeColor=green
```

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1, **остаётся запущенным** | нет |
| green | v2 | весь |

Старый цвет не удаляется - он остаётся как страховка для мгновенного отката.

**Шаг 6b. Тесты упали - откатываем**

`activeColor` не меняется вообще, вызывается `rollback.sh`, который выключает
green.

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1 | весь, как и был |
| green | выключен | нет |

**Пользователи не заметили ничего.** Сломанная версия жила несколько минут, не
получив ни одного пользовательского запроса.

## Четыре релиза подряд: полная картина

Самая наглядная часть. Три успешных выката и один сломанный, с состоянием
кластера после каждого шага.

### Релиз 1 - первый выкат

Кластер пустой, активного цвета нет, скрипт идёт по ветке первого релиза.

```
Service orders-service  ──selector: color=blue──>  [blue] v1  ██ ██
Service ...-preview     ──selector: color=green─>  [green] выключен
```

| Цвет | Версия | Поды | Трафик |
|---|---|---|---|
| blue | v1 | 2 | **весь** |
| green | - | 0 | нет |

Preview никуда не ведёт, подов green нет. Это нормальное состояние.

### Релиз 2 - выкатываем v2

**Шаг 1.** Активный цвет `blue`, значит цель - `green`.
**Шаг 2.** Тег работающего blue - `v1`, запоминаем, чтобы не сломать.
**Шаг 3.** Разворачиваем green с v2, `activeColor` остаётся blue:

```
Service orders-service  ──color=blue──>   [blue] v1  ██ ██   ← пользователи здесь
Service ...-preview     ──color=green──>  [green] v2 ██ ██   ← поднялся, трафика нет
```

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1 | **весь** |
| green | v2 | нет |

**Шаг 5.** E2E идут через preview, то есть против green:

```
[e2e] auth=auth-service orders=orders-service-preview web=web-client
e2e PASSED
```

**Шаг 6.** Переключаем `activeColor` на green:

```
Service orders-service  ──color=green──>  [green] v2 ██ ██  ← пользователи здесь
Service ...-preview     ──color=blue───>  [blue] v1  ██ ██  ← остался как страховка
```

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v1 | нет, но **работает** |
| green | v2 | **весь** |

Blue не удалён: если проблема всплывёт через пять минут, откат - это возврат
одного поля селектора, поды уже готовы принимать трафик.

### Релиз 3 - выкатываем v3, роли меняются

Активен green, значит цель - blue.

**Выкатили blue с v3, трафик пока на green:**

```
Service orders-service  ──color=green──>  [green] v2 ██ ██  ← пользователи
Service ...-preview     ──color=blue───>  [blue] v3  ██ ██  ← новый, проверяется
```

Обрати внимание: blue переехал с v1 сразу на v3. Промежуточная v2 на нём никогда
не жила, она была на green.

**После успешных тестов и переключения:**

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v3 | **весь** |
| green | v2 | нет, работает |

Цвета поменялись ролями. Так они и чередуются: blue, green, blue, green.

### Релиз 4 - выкатываем сломанную v4

Активен blue с v3, цель - green.

**Шаг 3.** Разворачивается green с v4, где `FAIL_MODE=1`:

```
Service orders-service  ──color=blue──>   [blue] v3  ██ ██  ← пользователи здесь
Service ...-preview     ──color=green──>  [green] v4 ██ ██  ← сломанный, трафика нет
```

Важно: поды v4 **успешно поднялись**. Процесс запустился, `/health` и `/ready`
отвечают. Первый предохранитель не сработал - с точки зрения Kubernetes всё в
порядке.

**Шаг 5.** E2E через preview падают:

```
[e2e] orders=orders-service-preview
e2e FAILED: an order can be created
```

Тест пытается создать заказ и получает 500 вместо 201.

**Шаг 6b.** Скрипт перехватывает провал:

```
e2e FAILED against green, user traffic never left blue
[rollback] restoring blue as the only serving colour
[rollback] done, Service now selects colour: blue
```

**После отката:**

| Цвет | Версия | Трафик |
|---|---|---|
| blue | v3 | **весь, не прерывался** |
| green | выключен | нет |

Сломанная версия прожила минуты три и не получила ни одного пользовательского
запроса.

### Сводка по четырём релизам

| Релиз | blue | green | Активен | Итог |
|---|---|---|---|---|
| 1 | v1 | - | blue | первый выкат |
| 2 | v1 | v2 | blue в **green** | переключение |
| 3 | **v3** | v2 | green в **blue** | переключение |
| 4 | v3 | ~~v4~~ | blue | откат, цвет не менялся |

### Какой предохранитель на какой случай

| Что сломалось | Когда заметно | Кто реагирует | Пользователь пострадал |
|---|---|---|---|
| образ не стартует, опечатка в переменной | поды не проходят readiness | Helm `--atomic` | нет |
| логика сломана, но процесс жив | e2e против preview | `deploy.sh` | нет |
| проблема всплыла через час после релиза | мониторинг, жалобы | `rollback.sh` вручную | да |

Релиз 4 - второй случай. Первый мы тоже поймали вживую, когда поды не стартовали
из-за `USER node`.

### Как посмотреть состояние в работающем кластере

```bash
# какой цвет сейчас обслуживает пользователей
kubectl -n lab get svc -o custom-columns=NAME:.metadata.name,COLOR:.spec.selector.color

# какие цвета подняты и с какими образами
kubectl -n lab get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image
```

Чтобы увидеть переключение вживую на локальном кластере, достаточно выполнить
выкат с тем же тегом, что уже развёрнут:

```bash
bash infra/scripts/deploy.sh orders-service local-b51f62a
```

Скрипт поднимет второй цвет, прогонит e2e через preview и переключит трафик. В
Grafana на панели по цветам это будет видно как переход.

## Три уровня отката

| Уровень | Что случилось | Кто реагирует | Видел ли пользователь проблему |
|---|---|---|---|
| **1** | поды не поднялись (ошибка конфигурации, образ не стартует) | Helm через `--atomic` | нет |
| **2** | поды поднялись, но e2e упали | `deploy.sh` не переключает трафик | нет |
| **3** | проблему заметили уже после переключения | `rollback.sh` вручную | да, какое-то время |

Первые два уровня срабатывают **автоматически** и полностью прозрачны для
пользователей. Третий - ручной, на случай проблемы, которую тесты не поймали.

### Уровень 1 в реальности

Это не теория: на одном из прогонов CD поды auth-service не смогли стартовать,
потому что в Dockerfile был `USER node`, а Kubernetes при `runAsNonRoot` требует
числовой идентификатор. Helm подождал 5 минут, не дождался готовности и откатил
релиз сам:

```
Error: release auth-service failed, and has been uninstalled due to atomic being set
```

Причину нашли в собранной диагностике, заменили на `USER 1000`, и в CI появилась
проверка, чтобы это не повторилось.

### Уровень 2 в реальности

Проверяется намеренно: запуск CD с флагом `fail_mode` разворачивает
orders-service с переменной `FAIL_MODE=1`, при которой сервис отвечает ошибкой
500 на все запросы к заказам. В логе видно:

```
colour serving traffic before the broken release: blue
green is ready but receives no user traffic yet
e2e FAILED against green, user traffic never left blue
colour serving traffic after the failed release: blue
```

Одинаковый цвет в первой и последней строке - и есть доказательство.

### Почему preview Service принципиален

Без него единственный способ проверить новую версию - сначала переключить на неё
трафик, а потом тестировать. То есть на пользователях.

Preview даёт отдельную точку входа в неактивный цвет, доступную только изнутри
кластера. Тесты ходят туда, пользователи - нет.

Это главное отличие нашей реализации от схемы «выкатили и проверили».

## Чарт postgresql

**StatefulSet**, а не Deployment - принципиальная разница: у StatefulSet
стабильное имя пода (`postgresql-0`) и постоянный том, который переживает
перезапуск. Для базы это обязательно.

Пароль берётся из общего секрета `lab-secrets` через `secretKeyRef`, в чарте его
нет. Service имеет тип `ClusterIP`, то есть база доступна только изнутри
кластера.

Probes используют `pg_isready` - штатную утилиту PostgreSQL.

## Как собираются метрики: полная цепочка

Участвуют два разных инструмента, и их легко перепутать:

- **Prometheus** - собирает и хранит числа
- **Grafana** - рисует по ним графики, сама ничего не собирает

### Шаг 1. Сервис считает свои метрики

В коде каждого сервиса есть `src/metrics.js`, он подключает библиотеку
`prom-client`. Она создаёт два счётчика:

| Метрика | Что считает |
|---|---|
| `http_requests_total` | сколько было запросов, с разбивкой по методу, маршруту и коду ответа |
| `http_request_duration_seconds` | сколько времени занял каждый запрос |

Middleware перехватывает каждый входящий запрос и по его завершении увеличивает
счётчики.

### Шаг 2. Сервис отдаёт метрики по HTTP

Эндпоинт `/metrics` возвращает обычный текст:

```
http_requests_total{method="POST",route="/orders",status="201"} 17
http_request_duration_seconds_bucket{le="0.05"} 15
```

Это формат Prometheus. Посмотреть можно самому:

```bash
kubectl -n lab port-forward svc/orders-service 3002:3000
curl http://localhost:3002/metrics
```

### Шаг 3. Под помечается аннотациями

В `deployment.yaml` каждому поду проставляются аннотации:

```yaml
prometheus.io/scrape: "true"
prometheus.io/port: "3000"
prometheus.io/path: "/metrics"
```

Это не магия Kubernetes - обычные пометки. Смысл им придаёт конфигурация
Prometheus.

### Шаг 4. Prometheus находит поды сам

В `prometheus-config.yaml` задано `kubernetes_sd_configs` с `role: pod` -
Prometheus запрашивает у Kubernetes список всех подов namespace `lab`. Именно для
этого ему нужны права из `monitoring-rbac.yaml`.

Дальше идут `relabel_configs` - правила обработки найденных подов:

| Правило | Что делает |
|---|---|
| `keep` по аннотации `scrape` | отбрасывает поды без пометки `scrape: "true"` |
| `replace` для адреса | подставляет порт из аннотации `port` |
| `replace` для пути | подставляет путь из аннотации `path` |
| копирование метки `app` | превращает её в лейбл `service` |
| копирование метки `color` | превращает её в лейбл `color` |

Последние два правила - самое интересное. Они переносят метки пода в метрики,
поэтому в запросах можно фильтровать по сервису и **по цвету**. Именно на этом
построена панель, показывающая переключение blue-green.

**Главное следствие:** при выкате нового цвета Prometheus подхватывает его
автоматически. Конфигурацию мониторинга менять не нужно - новый под просто
появляется в списке с нужными аннотациями.

Проверить, кого нашёл Prometheus: http://localhost:9090/targets

### Шаг 5. Prometheus опрашивает и хранит

Раз в 10 секунд (`scrapeInterval`) он ходит на `/metrics` каждого найденного пода
и складывает значения в свою базу временных рядов. Хранит час - для лабораторной
больше не нужно, данные не переживают пересоздание кластера.

### Шаг 6. Grafana берёт данные из Prometheus

При старте Grafana читает два ConfigMap:

| ConfigMap | Что настраивает |
|---|---|
| `grafana-datasources` | источник данных: адрес `http://prometheus:9090` |
| `grafana-dashboards` | сам дашборд из файла `dashboards/lab.json` |

Этот механизм называется **provisioning**: дашборд не создаётся руками через
интерфейс, а описан файлом в репозитории. Пересоздашь кластер - дашборд появится
сам, с теми же панелями.

### Шаг 7. Панели дашборда

| Панель | Запрос | Что показывает |
|---|---|---|
| Requests per second | `sum(rate(http_requests_total[1m])) by (service)` | нагрузка по сервисам |
| p95 duration | `histogram_quantile(0.95, ...)` | задержка без учёта выбросов |
| Error rate | `sum(rate(http_requests_total{status=~"5.."}[1m]))` | доля ошибок сервера |
| Pods by colour | `sum(up) by (service, color)` | сколько подов какого цвета работает |

`rate(...[1m])` - скорость роста счётчика за минуту. Счётчик только растёт, сам
по себе он неинформативен; интересна именно скорость.

`up` - метрика, которую Prometheus создаёт сам: 1 если под ответил на опрос, 0
если нет. Поэтому последняя панель работает без какого-либо кода в приложении.

### Вся цепочка одной схемой

```
код сервиса (prom-client)
   │ считает запросы
   ▼
GET /metrics                     текст с числами
   │
   │ Prometheus раз в 10 секунд
   │ находит поды по аннотациям
   ▼
Prometheus (база временных рядов)
   │
   │ Grafana запрашивает по PromQL
   ▼
дашборд из dashboards/lab.json
```

## Что показать на защите про мониторинг

1. **http://localhost:9090/targets** - четыре пода найдены автоматически, у
   каждого лейблы `service` и `color`
2. **http://localhost:3000** - дашборд, панель `Scraped pods by colour`
3. Сказать: Prometheus не настроен на конкретные адреса, он находит поды по
   аннотациям, поэтому новый цвет при выкате подхватывается без правки конфигурации

Если спросят «зачем и Prometheus, и Grafana» - они делают разное: первый собирает
и хранит, второй визуализирует. Grafana без источника данных пуста.
