# Шпаргалка для защиты

## Что это за работа, в двух предложениях

Микросервисное приложение из трёх сервисов с полностью автоматизированным
конвейером доставки: от коммита в git до развёрнутой в Kubernetes версии, с
проверками безопасности, тестами, мониторингом и автоматическим откатом.
Прикладная логика намеренно простая - оценивается процесс доставки, а не
бизнес-функциональность.

---

## Термины

### Общие

| Термин | Определение |
|---|---|
| **CI** (Continuous Integration) | автоматическая проверка каждого изменения кода: линтеры, тесты, сборка |
| **CD** (Continuous Delivery/Deployment) | автоматическое развёртывание проверенного кода в среду исполнения |
| **Пайплайн** | последовательность автоматических шагов; у нас два файла в `.github/workflows/` |
| **Джоб** (job) | одна изолированная задача внутри пайплайна, например «прогнать тесты» |
| **Артефакт** | файл, сохранённый по итогам прогона (у нас - собранная диагностика кластера) |

### Контейнеры

| Термин | Определение |
|---|---|
| **Docker-образ** | неизменяемый шаблон с приложением и его зависимостями |
| **Контейнер** | запущенный экземпляр образа |
| **Dockerfile** | инструкция сборки образа |
| **Multi-stage сборка** | сборка в несколько этапов: инструменты остаются в промежуточном слое, в финальный образ попадает только нужное для запуска |
| **Тег образа** | метка версии; у нас `sha-<коммит>`, чтобы всегда знать, какой код развёрнут |
| **Реестр** (registry) | хранилище образов; у нас GHCR - GitHub Container Registry |

### Kubernetes

| Термин | Определение |
|---|---|
| **Kubernetes (k8s)** | система управления контейнерами: запускает, следит, перезапускает, масштабирует |
| **Кластер** | набор машин под управлением Kubernetes |
| **Под** (Pod) | минимальная единица запуска, один или несколько контейнеров |
| **Deployment** | описание желаемого состояния: какой образ и сколько реплик держать |
| **Service** | стабильный сетевой адрес для группы подов; направляет трафик по **селектору** - набору меток |
| **Namespace** | логический раздел кластера; у нас всё в namespace `lab` |
| **Secret** | объект для хранения паролей и ключей, подключается в под как переменные окружения |
| **Job** | одноразовая задача, которая должна выполниться и завершиться (у нас - миграции) |
| **kubectl** | утилита командной строки для работы с кластером |
| **kind** | Kubernetes IN Docker: настоящий кластер, запущенный внутри docker-контейнеров |
| **probe** | проверка состояния контейнера самим Kubernetes |
| **liveness probe** | «жив ли процесс»; при провале под перезапускается |
| **readiness probe** | «готов ли принимать трафик»; при провале под исключается из Service, но не перезапускается |
| **RBAC** | управление правами: кто и что может делать в кластере |
| **ServiceAccount** | «учётная запись» для программ, а не людей |

### Helm

| Термин | Определение |
|---|---|
| **Helm** | пакетный менеджер для Kubernetes: шаблонизирует манифесты и управляет версиями установки |
| **Чарт** (chart) | пакет с шаблонами манифестов |
| **values** | файл с параметрами, подставляемыми в шаблоны |
| **Релиз** (release) | конкретная установка чарта в кластер, с историей ревизий |
| **Хук** (hook) | действие, привязанное к этапу установки; у нас миграции выполняются хуком `pre-upgrade` |

### Стратегии выката

| Термин | Определение |
|---|---|
| **Blue-green** | две параллельные версии; трафик мгновенно переключается с одной на другую |
| **Canary** | новая версия получает часть трафика, доля постепенно растёт |
| **Rollback** | возврат к предыдущей рабочей версии |
| **Preview Service** | наш дополнительный Service, ведущий на неактивный цвет; нужен, чтобы проверить новую версию до переключения |

### Безопасность

| Термин | Определение |
|---|---|
| **SAST** | статический анализ исходного кода на уязвимости; у нас CodeQL |
| **SCA** | анализ зависимостей на известные уязвимости; у нас npm audit и Trivy |
| **CVE** | запись в публичном каталоге уязвимостей с уникальным номером |
| **gitleaks** | сканер, ищущий пароли и ключи в коде и истории коммитов |
| **Гейт** (gate) | условие, блокирующее продвижение по конвейеру |

### Наблюдаемость

| Термин | Определение |
|---|---|
| **Метрика** | числовой показатель работы системы во времени |
| **Prometheus** | собирает и хранит метрики, опрашивая сервисы по HTTP |
| **Scrape** | сам процесс опроса: Prometheus раз в 10 секунд читает `/metrics` |
| **Grafana** | рисует графики по данным из Prometheus |
| **p95** | значение, ниже которого лежат 95% запросов; показывает задержку без учёта редких выбросов |

### Тесты

| Термин | Определение |
|---|---|
| **Unit** | проверка отдельной функции в изоляции |
| **Integration** | проверка связки компонентов, у нас - код плюс настоящая PostgreSQL |
| **E2E** | проверка всей системы целиком, как её видит пользователь |

## Как устроено приложение

```
браузер
   │ http://localhost:8080
   ▼
web-client (nginx)         ← единственный, кто доступен снаружи
   ├─ /             отдаёт HTML-страницу
   ├─ /api/login  → auth-service   выдаёт JWT
   └─ /api/orders → orders-service проверяет JWT, читает и пишет заказы
                          │
                          ▼
                    PostgreSQL     доступна только внутри кластера
```

**JWT** - подписанный токен. auth-service подписывает его секретным ключом,
orders-service проверяет подпись тем же ключом. Ключ лежит в Kubernetes Secret,
оба сервиса читают его из переменной окружения.

## Устройство кластера: что где живёт

**Кластер один на всё.** Он не делится по сервисам - это вычислительная площадка
целиком, внутри которой живут все компоненты.

```
Кластер (один, называется lab)
│
├── Namespace kube-system        служебные компоненты самого Kubernetes
│   └── etcd, apiserver, scheduler, controller-manager, coredns
│
└── Namespace lab                наше приложение
    ├── Deployment auth-service-blue      (2 реплики)
    ├── Deployment orders-service-blue    (2 реплики)
    ├── Deployment web-client-blue        (1 реплика)
    ├── StatefulSet postgresql            (1)
    ├── Deployment prometheus             (1)
    ├── Deployment grafana                (1)
    └── Service auth-service, orders-service, web-client, postgresql
```

### Аналогия

| Понятие | Аналогия |
|---|---|
| Кластер | офисное здание |
| Узел (node) | этаж с рабочими местами |
| Namespace | отдел внутри здания |
| Deployment | штатное расписание: «нужно 2 оператора» |
| Под | конкретный сотрудник на месте |
| Service | внутренний номер отдела: звонишь на номер, попадаешь к свободному |

Не бывает «здания для бухгалтерии и здания для разработки» - это отделы внутри
одного здания.

### Компоненты самого Kubernetes

Живут в `kube-system`, появились вместе с кластером, их никто не разворачивал:

| Компонент | Роль |
|---|---|
| `kube-apiserver` | единственная точка входа, с ним говорит `kubectl` |
| `etcd` | база, где хранится всё состояние кластера |
| `kube-scheduler` | решает, на каком узле запустить под |
| `kube-controller-manager` | следит, чтобы реальность совпадала с желаемым |
| `coredns` | DNS: благодаря ему orders-service находит базу по имени `postgresql` |
| `kube-proxy`, `kindnet` | сеть между подами |

У нас **один узел**, совмещающий роли управления и запуска приложений. В
продакшене control plane выносят на отдельные машины, обычно три для
отказоустойчивости. Логика работы та же, отличается масштаб.

### Цвета есть не у всех

Blue-green применяется только к трём сервисам приложения:

| Компонент | Цвета | Почему |
|---|---|---|
| auth-service, orders-service, web-client | blue / green | выкатываются пайплайном |
| PostgreSQL | нет | база одна, оба цвета работают с ней же |
| Prometheus, Grafana | нет | инфраструктура, не выкатывается |

База принципиально не дублируется: иначе заказы, созданные на blue, не были бы
видны на green.

Цвета у сервисов **независимы**. В прогоне с переключением у orders-service был
`green`, а у двух других оставался `blue`.

### Сколько подов

| Состояние | Подов |
|---|---|
| сейчас (все на blue) | 8 работающих плюс завершённый Job миграций |
| при выкате одного сервиса | 10, после переключения старый цвет остаётся тёплым |
| если бы все три были в двух цветах | 13 |

Расчёт максимума: auth 2+2, orders 2+2, web-client 1+1, инфраструктура 3.

```bash
kubectl -n lab get pods -L color   # колонка color: у инфраструктуры пустая
kubectl get nodes                  # сколько узлов
kubectl get ns                     # какие namespace
```

### Что кластер даёт на практике

**Абстракция от железа.** Ты говоришь «хочу 2 копии этого образа», а не «запусти
на сервере 3». Узел вышел из строя - поды переехали сами.

**Декларативность.** Описываешь, *что* должно быть, а не *как* этого добиться.
Контроллеры постоянно сверяют реальность с описанием. Убьёшь под руками - через
секунду появится новый. На этом же построен откат: меняешь описание, кластер сам
приводит себя в соответствие.

**Единая точка управления.** Весь кластер описывается YAML-файлами - отсюда
«инфраструктура как код»: состояние лежит в git, а не в чьей-то памяти.

## Как работает конвейер в GitHub

### Что такое workflow

Файл с инструкциями в `.github/workflows/`: при каком событии запускаться и какие
команды выполнить. При наступлении события GitHub берёт **чистую виртуальную
машину** в своём облаке, скачивает на неё код, выполняет шаги и затем машину
уничтожает.

У нас два таких файла - `ci.yml` и `cd.yml`.

### CI и CD - в чём разница

| | CI | CD |
|---|---|---|
| Отвечает на вопрос | «код корректный?» | «система работает после развёртывания?» |
| Что делает | проверяет и собирает образы | разворачивает и проверяет вживую |
| Когда запускается | на каждый push и pull request | после успешного CI на `main`, либо вручную |
| Чем заканчивается | образы лежат в реестре | e2e прошли, кластер уничтожен |

CI заканчивается тем, что образы опубликованы. CD берёт уже готовые образы и
разворачивает их.

### Джобы CI и что они проверяют

| Джоб | Что делает |
|---|---|
| `Lint` | стиль и очевидные ошибки в коде |
| `Unit tests` | отдельные функции в изоляции |
| `Integration tests` | код вместе с настоящей PostgreSQL |
| `SAST (CodeQL)` | ищет уязвимости в **нашем** коде |
| `SCA (npm audit + Trivy)` | ищет уязвимости в **чужих** библиотеках, которые мы подключили |
| `Secret scan (gitleaks)` | ищет пароли и ключи в коде и во всей истории коммитов |
| `Policy checks` | наши собственные правила: нет тега `latest`, `USER` задан числом |
| `Helm` | чарты корректны: `helm lint` плюс рендеринг шаблонов |
| `Build and push` | собирает образы, сканирует их Trivy, публикует в реестр |

Разница SAST и SCA: первый читает код, который написали мы, второй смотрит на
зависимости. Уязвимость чаще приходит именно из зависимостей.

Зачем `Policy checks` отдельно: эти правила не ловятся ни линтером, ни сборкой.
Образ с `USER node` собирается нормально, но под с ним не стартует в Kubernetes -
ошибка видна только в работающем кластере, поэтому вынесена в отдельную проверку.

### Что происходит при Run workflow

1. GitHub выделяет чистую виртуалку
2. Скачивает код из `main`
3. Создаёт **новый kind-кластер** прямо на ней
4. Скачивает образы из реестра по указанному тегу
5. Разворачивает PostgreSQL, Prometheus, Grafana
6. Выкатывает три сервиса через `deploy.sh`
7. Прогоняет e2e
8. Выполняет демонстрацию переключения или отката
9. **Уничтожает виртуалку вместе с кластером**

Кластер каждый раз новый - отсюда и необходимость отдельного шага для показа
переключения: одного релиза в пустом кластере для этого недостаточно.

### Packages в GitHub - это что

Это GHCR, реестр Docker-образов. Три пакета `auth-service`, `orders-service`,
`web-client` создал джоб `Build and push`. Внутри каждого - версии с тегами вида
`sha-42af804`.

Зачем нужен реестр: собранный образ надо где-то хранить, чтобы кластер мог его
скачать.

```
код в git → CI собирает образ → образ в GHCR → CD скачивает и разворачивает
```

Локально образы в реестр не попадают: `kind-up.sh` собирает их и сразу кладёт в
кластер командой `kind load`, минуя реестр.

### Почему развёрнутое в CD нельзя открыть в браузере

Кластер существует только во время прогона, минут пять, на виртуалке внутри
инфраструктуры GitHub. Публичного адреса у неё нет, после окончания прогона нет
ни машины, ни кластера.

**CD доказывает не доступность, а воспроизводимость развёртывания.** Это разные
вещи:

| Вопрос | Кто отвечает |
|---|---|
| Можно ли развернуть систему с нуля на чистой машине? | CD |
| Работает ли она после развёртывания? | e2e внутри CD |
| Можно ли зайти по адресу и потыкать? | локальный кластер |

При этом в CD ничего не имитируется: создаётся настоящий кластер, применяются
настоящие миграции, e2e делают настоящие HTTP-запросы, blue-green реально
переключает трафик. Временная только среда. Аналогия - тест-драйв: машина реально
едет, просто потом её возвращают в салон.

### Зачем CD, если можно развернуть локально

Локальный запуск отвечает «работает у меня». CD отвечает «работает у любого на
чистой машине». Локально всё может работать потому, что полгода назад что-то было
настроено и забыто. CD начинает с пустой виртуалки, где нет ничего.

Плюс CD запускается сам при каждом изменении в `main` - никто не забудет шаг и не
развернёт не ту версию.

## Структура проекта

```
auth-service/          выдаёт JWT по логину и паролю
orders-service/        заказы в PostgreSQL, проверяет JWT, здесь же миграции
web-client/            страница на nginx, он же прокси к двум сервисам
infra/                 вся инфраструктура
e2e/                   сквозной тест против развёрнутой системы
.github/workflows/     два пайплайна: CI и CD
docs/                  документация
```

### Внутри сервиса (на примере orders-service)

| Путь | Что это |
|---|---|
| `src/app.js` | маршруты HTTP: `/orders`, `/health`, `/ready`, `/metrics` |
| `src/server.js` | точка входа, запускает сервер на порту |
| `src/db.js` | пул соединений с PostgreSQL |
| `src/auth.js` | проверка JWT во входящих запросах |
| `src/migrate.js` | применение миграций, ведёт таблицу `schema_migrations` |
| `src/metrics.js` | счётчики и гистограммы для Prometheus |
| `migrations/*.sql` | сами миграции, применяются по возрастанию имени |
| `test/app.test.js` | unit-тесты, без базы |
| `test/integration.test.js` | тесты против настоящей PostgreSQL |
| `Dockerfile` | multi-stage сборка, запуск от `USER 1000` |
| `eslint.config.js` | правила линтера |

У `auth-service` то же самое без базы и миграций. У `web-client` только
`nginx.conf`, `public/index.html` и Dockerfile.

| Файл | Что генерирует |
|---|---|
| `templates/deployment.yaml` | по одному Deployment на каждый включённый цвет |

| `values.yaml` | значения по умолчанию для всех сервисов |

## Скрипты: что делает каждый

| Скрипт | Запускается | Что делает |
|---|---|---|
| **`deploy.sh`** | в CD и локально | **основной**. Определяет активный цвет, выкатывает противоположный, гоняет e2e против preview, переключает трафик только при успехе |
| **`rollback.sh`** | вызывается из `deploy.sh` при падении e2e, либо вручную | возвращает трафик на указанный цвет, выключает второй |
| **`run-e2e.sh`** | вызывается из `deploy.sh` и из CD | пробрасывает порты сервисов на localhost и запускает `e2e/run.js` |
| **`kind-up.sh`** | только локально | поднимает весь стек с нуля: кластер, секреты, база, мониторинг, три сервиса |

Важная деталь: `kind-up.sh` **не содержит своей логики выката** - он вызывает тот
же `deploy.sh`, что работает в пайплайне. Поэтому локальная демонстрация и CD
делают одно и то же.

### Как вызываются

```bash
bash infra/scripts/deploy.sh orders-service sha-abc1234
bash infra/scripts/rollback.sh orders-service blue
bash infra/scripts/run-e2e.sh orders-service   # через preview этого сервиса
bash infra/scripts/kind-up.sh
```

## Что делали, по этапам

**A. Репозиторий.** Монорепозиторий с четырьмя каталогами: три сервиса и `infra`.
Каждый сервис самодостаточен: свой Dockerfile, свои тесты, свои зависимости.

**B. CI.** Девять джобов. Восемь проверок идут параллельно, сборка образов
объявляет их все в зависимостях и не стартует, пока хоть одна красная. Образы
сканируются Trivy **до** публикации в реестр.

**C. CD.** Пять Helm-чартов. Три сервиса разворачиваются одним параметризованным
чартом с разными values - чтобы логика blue-green существовала в одном экземпляре,
а не в трёх копиях. Миграции выполняются хуком перед стартом новых подов.

**D. Наблюдаемость.** Сервисы отдают метрики на `/metrics`, Prometheus находит их
по аннотациям подов, Grafana рисует четыре панели. При падении деплоя пайплайн
собирает логи в артефакт.

**E. Безопасность.** Секреты в GitHub Secrets, в кластер попадают как Kubernetes
Secret. gitleaks проверяет всю историю коммитов. Теги `latest` запрещены на двух
уровнях. CD работает под ограниченным ServiceAccount, а не под администратором.

---

## Три уровня отката

| Уровень | Когда срабатывает | Что делает |
|---|---|---|
| 1 | поды новой версии не проходят readiness | Helm сам возвращает релиз (`--atomic`) |
| 2 | e2e упали против preview | селектор не переключается, новая версия выключается |
| 3 | нужно отменить уже переключённый релиз | `rollback.sh` возвращает селектор назад |

**Второй уровень главный.** Проверка идёт до переключения трафика, поэтому
пользователи не видят сломанную версию ни секунды.

### Показ, 7-10 минут

**1. Приложение (1 мин).** http://localhost:8080 - войти, создать заказ.
Сказать: три сервиса, наружу открыт только фронтенд, база доступна лишь изнутри.

**2. Репозиторий и CI (2 мин).**
[Прогон 34376165898](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34376165898) -
показать структуру каталогов и граф джобов. Подчеркнуть: `Build and push` зависит
от всех восьми проверок и не стартует, пока они не пройдут.

**3. Гейт безопасности (1 мин).**
[Прогон 34347366212](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34347366212) -
три красных джоба `Build and push`, Trivy заблокировал публикацию из-за CRITICAL
CVE. Сказать: уязвимость устранена обновлением базового образа, а не подавлением.

**Почему показываем именно провал.** Требование B5 звучит «запретить пуш при
критических уязвимостях». Зелёный прогон этого не доказывает: если уязвимостей не
нашлось, гейт просто не срабатывал, и непонятно, сработал бы вообще. Аналогия -
пожарная сигнализация, которая ни разу не звонила, не доказывает свою
исправность.

Ключевая деталь - **порядок шагов внутри джоба**:

```
1. docker build     собрали образ локально
2. trivy scan       нашли CRITICAL → джоб падает
3. docker push      ← до этого шага не дошло
```

Сканирование стоит между сборкой и публикацией, поэтому уязвимый образ физически
не попал в реестр. Показывать лучше парой: красный прогон (гейт сработал) плюс
скриншот `b4` с пакетами в GHCR (после исправления образы опубликованы).

Второй такой же по смыслу кадр - `e2-gitleaks`: красный `Secret scan` доказывает,
что проверка секретов работает. Оба красных прогона показываются намеренно.

**4. Blue-green (2 мин).**
[Прогон 34378646260](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34378646260),
шаг `Demonstrate a blue-green switch`. Показать последовательность в логе:

```
before the switch: blue
green is ready but receives no user traffic yet
[e2e] orders=orders-service-preview      ← проверка идёт через preview
e2e PASSED
switching traffic to green
after the switch: green
```

Затем локально:
```bash
kubectl -n lab get svc -o custom-columns=NAME:.metadata.name,COLOR:.spec.selector.color
```

**Важно: e2e запускаются ДО переключения, а не после.** В CD их два прогона с
разными целями, и это видно по номерам строк в логе:

| Строка лога | Прогон | Через что | Отвечает на вопрос |
|---|---|---|---|
| 571 | первый | `orders=orders-service` (живой) | система развернулась и работает |
| 622 | второй | `orders=orders-service-preview` | новая версия годна к переключению |

Порядок строк во втором прогоне: `green is ready but receives no user traffic yet`
(621) → `[e2e] orders=orders-service-preview` (622) → `e2e PASSED` (633) →
`switching traffic to green` (634). Тесты прошли **между** готовностью нового
цвета и переключением.

Почему первый прогон идёт после развёртывания: при первом релизе переключать
нечего, preview ведёт на `green`, которого ещё не существует.

Если бы e2e шли только после переключения, схема была бы обычным «выкатили и
проверили»: сломанная версия успела бы обслужить пользователей. Preview даёт
возможность проверить раньше - на этом и держится второй уровень отката.

**5. Откат (2 мин).**
[Прогон 34580277531](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34580277531),
шаг `Break orders-service on purpose and prove the rollback works`. Главное в
кадре - одинаковый цвет в строках `before the broken release` и `after the failed
release`: трафик остался на рабочей версии.

**Про галочку `fail_mode`.** Да, сценарий запускается вручную с флагом, и это
честно проговаривается. Важно разделить, что искусственное, а что настоящее:

| Искусственное | Настоящее |
|---|---|
| переменная `FAIL_MODE` в коде orders-service | обнаружение проблемы (e2e) |
| галочка в форме запуска workflow | логика отката (`deploy.sh`, `rollback.sh`) |
| шаг, который подменяет значение в секрете | переключение трафика |

**`deploy.sh` ничего не знает про `fail_mode`** - он выполняет ту же
последовательность, что при обычном релизе. Подменена ровно одна переменная
окружения приложения. Аналогия: учебная пожарная тревога, дым искусственный,
эвакуация настоящая.

Почему без флага не обойтись: чтобы показать откат, нужна сломанная версия.
Коммитить сломанный код - он останется в истории; ломать руками в кластере -
невоспроизводимо. Переменная окружения оставляет код чистым и даёт повторяемый
сценарий.

Сильный контраргумент на «вы же сами и сломали»: **первый уровень отката сработал
на настоящей ошибке**, которую никто не подстраивал - поды не стартовали из-за
`USER node`, и Helm откатил релиз сам
([прогон 34358039730](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34358039730)).
То есть один откат воспроизведён намеренно, другой случился по-настоящему.

И сам шаг с `fail_mode` - это не показ, а **тест механизма**: он валит сборку,
если сломанный релиз был принят или если цвет всё-таки сменился.

**6. Мониторинг (1 мин).** Grafana: всплеск запросов от только что созданных
заказов. Отдельно панель `Scraped pods by colour` - на ней видно момент

**6б. Запросы в Prometheus - опционально, если попросят показать сырые данные.**

Открыть http://localhost:9090/graph и вставить один из трёх:

```
up
```
Самый простой. Возвращает 1 для каждого пода, который ответил на опрос, и 0 для
недоступного. **Ожидаемо увидеть:** четыре строки со значением 1 - по два пода
auth-service и orders-service. Доказывает, что сбор метрик реально идёт.

```
sum(up) by (service, color)
```
Те же поды, сгруппированные по сервису и цвету. **Ожидаемо увидеть:**
`{service="orders-service", color="blue"} 2`. Это ровно тот запрос, что питает
панель blue-green: в момент переключения появляется вторая строка с другим
цветом.

```
sum(rate(http_requests_total[1m])) by (service)
```
Скорость запросов за последнюю минуту. **Ожидаемо увидеть:** ненулевые значения,
если только что кликал в приложении, и близкие к нулю, если система простаивала.
Счётчик `http_requests_total` только растёт, поэтому интересна не его величина, а
скорость роста - её и даёт `rate`.

Если хочется показать всю цепочку от сырых данных к графику, порядок такой:
`/metrics` одного сервиса (текст с числами) → `/targets` (кого Prometheus нашёл)
→ Grafana (что из этого получилось).

**8. Безопасность: RBAC и запрет latest (1 мин).**

**RBAC (пункт E4).** Шаг `Prove the deployer has no cluster-wide rights` в
[успешном CD](https://github.com/ivanribin/lab-cicd-microservices/actions/runs/34376411954):

```
create deployment in lab: yes
list nodes (cluster-wide): no
create deployment in kube-system: no
```

Читается так: в своём namespace работать может, за его пределы не выходит, к
системным компонентам доступа не имеет.

*Где описаны права:* `infra/k8s/rbac.yaml`, четыре объекта - ServiceAccount
(«кто»), Role («что можно»), RoleBinding (связывает их) и Secret с токеном.
Схема RBAC требует всех трёх: аккаунт без привязки прав не имеет, роль сама по
себе никому не выдана.

*Как workflow их получает* - цепочка в `cd.yml`:

```
1. Apply namespace and RBAC       kubectl apply -f infra/k8s/rbac.yaml
                                  ← выполняется ПОД АДМИНИСТРАТОРОМ kind
2. Create application secrets     ← тоже под администратором
3. Build a restricted kubeconfig  достаёт токен из Secret, собирает kubeconfig
                                  echo "KUBECONFIG=..." >> $GITHUB_ENV
                                  ← с этой строки личность сменилась
4. Prove the deployer has no...   ← уже под cicd-deployer
5. Install PostgreSQL, деплой...  ← всё дальше под cicd-deployer
```

**Почему RBAC применяет администратор.** Деплойщик намеренно не имеет прав
создавать роли - иначе он выдал бы себе что угодно, и ограничение потеряло бы
смысл. Поэтому роли создаёт администратор, а пайплайн затем «понижает себя в
правах». Аналогия: пропуск оформляет служба безопасности, а не сам сотрудник.

Это же ограничение объясняет, почему `monitoring-rbac.yaml` вынесен из чарта:
чарт ставится деплойщиком, а роли для Prometheus он создать не может.

**Что делает это доказательством, а не декларацией:** шаг проверки не просто
печатает права, он валит сборку, если их окажется больше:

```bash
if [ "$(kubectl auth can-i list nodes)" != "no" ]; then
  echo "::error::the deployer must not have cluster-wide access"
  exit 1
fi
```

**Запрет latest (пункт E3).** Зелёный CI, джоб `Policy checks`, строка
`no latest tags found in infra/`. Плюс скриншот `b4` с тегами `sha-*` в GHCR.

Запрет на двух уровнях, они ловят разное:

| Уровень | Где | Что ловит |
|---|---|---|
| чарт | `_helpers.tpl`, вызов `fail` | ручной `helm install` мимо пайплайна |
| CI | `Policy checks`, `grep` по `infra/` | `latest`, вписанный в манифест или values |

Нужны оба, потому что множества не совпадают: CI проверяет закоммиченное, а
helper - то, что реально разворачивается, ведь тег подставляется скриптом в
момент выката.

*Почему `latest` вообще проблема:* это имя тега, а не «самая новая версия». Образ
под ним меняется во времени, поэтому непонятно, какой код работает, откат
невозможен, а два пода, запущенные в разное время, могут работать на разных
образах с одинаковым тегом. У нас тег равен хешу коммита.

**9. Probes и устройство кластера - если спросят про Kubernetes.**

Показать вживую:

```bash
kubectl -n lab describe pod $(kubectl -n lab get pods -l app=orders-service -o jsonpath='{.items[0].metadata.name}') | grep -E "Liveness|Readiness|Ready:"
```

Ожидаемый вывод:

```
Ready:          True
Liveness:   http-get http://:http/health delay=3s period=5s #failure=3
Readiness:  http-get http://:http/ready  delay=3s period=5s #failure=3
```

Читается так: через 3 секунды после старта Kubernetes начинает каждые 5 секунд
дёргать эндпоинт и после 3 неудач подряд считает проверку проваленной.

**Сколько у нас подов.** `blue` и `green` - это не поды, а Deployment, то есть
описания «хочу столько-то копий». Иерархия:

```
Deployment            ReplicaSet           Pods
"хочу 2 копии"   →    следит за числом →   реально запущенные контейнеры
```

Сейчас в кластере 9 подов: по 2 у auth-service и orders-service, 1 web-client,
1 PostgreSQL, 1 Prometheus, 1 Grafana и завершённый Job миграций. При выкате
второго цвета станет 11 - это и есть цена blue-green, обе версии живут
одновременно.

```bash
kubectl -n lab get deploy    # сколько копий заказано
kubectl -n lab get pods      # что реально работает
```

**Что значит «под убирается из Service».** Не выключается, а исключается из
списка адресов, по которым Service распределяет трафик:

```bash
kubectl -n lab get endpoints orders-service
```

Там ровно столько адресов, сколько подов прошли readiness. Провалил проверку -
адрес исчез, трафик пошёл на оставшиеся. Под при этом продолжает работать, его
продолжают опрашивать, и он вернётся в список сам.

Аналогия: кассир на месте и жив, но у него завис терминал - ставит табличку
«касса не работает», покупателей направляют к соседней. Починил - табличку убрал.

**Про Chart.yaml и values.yaml**, если спросят по чартам: оба файла нужны Helm,
а не Kubernetes. В кластер уходят только отрендеренные манифесты.

| | Chart.yaml | values.yaml |
|---|---|---|
| что это | паспорт пакета: имя, версия | параметры: образ, порты, реплики, цвета |
| меняется | почти никогда | при каждом релизе |

Показать, что реально уходит в кластер:

```bash
helm template orders-service infra/helm/microservice -f infra/helm/values/orders-service.yaml --set colors.blue.tag=sha-42af804
```

В выводе нет ни слова из `Chart.yaml` - только чистые манифесты Kubernetes.

## Вероятные вопросы

**Почему blue-green, а не canary?**
Задание разрешает любую из двух. Blue-green переключает трафик атомарно, поэтому
не бывает состояния, когда часть пользователей на сломанной версии. Плюс откат -
это возврат одного поля селектора.

**Почему кластер kind, а не облако?**
Задание требует развёртывание в Kubernetes, не уточняя, какой. kind - настоящий
Kubernetes, просто запущенный в контейнерах. Один и тот же скрипт работает и в
пайплайне, и локально.

**Почему в CD каждый раз новый кластер?**
Так проверяется весь путь с нуля, включая создание namespace, секретов и
миграций. Побочный эффект: демонстрация переключения требует второго релиза
внутри того же прогона, для этого есть отдельный шаг.

**Почему один чарт на три сервиса?**
Логика blue-green одинакова для всех. В трёх копиях она неизбежно разошлась бы
при первой правке. Различия вынесены в три файла values.

**Зачем preview Service?**
Чтобы прогнать e2e против новой версии до того, как она получит пользовательский
трафик. Без него проверка шла бы уже после переключения, то есть на пользователях.

**Почему красный прогон - это доказательство?**
Зелёный пайплайн не доказывает, что защита срабатывает: возможно, она просто ни
разу не понадобилась. Красный показывает механизм в действии.

**Как секреты попадают в приложение?**
GitHub Secrets → шаг пайплайна создаёт Kubernetes Secret → под получает значения
через `secretKeyRef`. В коде и чартах их нет, gitleaks проверяет это на каждом
коммите.

**Почему запрещён тег latest?**
По `latest` невозможно понять, какой код работает в кластере, и откат становится
неоднозначным. У нас тег равен хешу коммита. Запрет реализован и в чарте, и в CI.

**Что будет, если упадёт база?**
Readiness probe у orders-service делает запрос к базе. Под перестанет считаться
готовым и будет исключён из балансировки, но не перезапустится - перезапуск не
чинит недоступную базу.

**Чем отличаются liveness и readiness?**
Liveness отвечает на вопрос «жив ли процесс» и приводит к перезапуску. Readiness -
«готов ли обслуживать» и управляет тем, идёт ли на под трафик. На readiness
построен механизм выката: пока новые поды не готовы, релиз не считается успешным.

**Почему liveness не проверяет базу, а readiness проверяет?**
Если бы liveness зависела от базы, недоступность базы вызывала бы бесконечные
перезапуски подов - а перезапуск базу не чинит, только мешает ей восстановиться.
Правило: liveness не должна зависеть от внешних систем. Readiness зависеть может,
её задача как раз убрать под из балансировки до восстановления.

**Сколько подов в кластере и что такое blue?**
`blue` - это Deployment, описание «хочу N копий такого образа», а не под. Внутри
него 2 пода у backend-сервисов и 1 у web-client. Всего в кластере 9 подов, при
выкате второго цвета становится 11.

**Зачем по две реплики?**
Отказоустойчивость: упал один под - трафик идёт на второй. Плюс на двух репликах
видно работу readiness: один под может выпасть из балансировки, второй продолжит
обслуживать.

**Почему сломанную версию запускают вручную галочкой?**
Чтобы показать откат, нужна сломанная версия, но портить рабочий код ради этого
нельзя. Переменная окружения даёт воспроизводимый сценарий и оставляет код
чистым. При этом сам механизм отката не трогается: `deploy.sh` не знает про
`fail_mode` и работает как при обычном релизе.

**Chart.yaml и values.yaml - это конфигурация Kubernetes?**
Нет, оба файла нужны Helm. Kubernetes получает только отрендеренные из шаблонов
манифесты и про Helm ничего не знает. Chart.yaml - паспорт пакета (имя, версия),
values.yaml - параметры подстановки.

**E2E идут до или после переключения трафика?**
До. В CD два прогона: первый после развёртывания через живые Service (проверяет,
что система вообще поднялась), второй внутри `deploy.sh` через preview Service -
до переключения. Именно второй решает, переключать трафик или откатывать.

**Откуда workflow берёт права из `infra/k8s/rbac.yaml`?**
Шаг `Apply namespace and RBAC` применяет файл через `kubectl apply` под
администратором кластера. Следующий шаг достаёт токен ServiceAccount из Secret,
собирает из него отдельный kubeconfig и записывает путь в `$GITHUB_ENV` - с этого
момента все команды идут от имени ограниченного аккаунта. CI (`ci.yml`) к
кластеру доступа не имеет вообще.

**Почему RBAC применяется под администратором, а не деплойщиком?**
У деплойщика намеренно нет прав создавать роли: аккаунт, способный это делать,
может выдать себе любые привилегии. Поэтому роли создаёт администратор, а
пайплайн после этого переключается на ограниченную учётную запись.

**У вас отдельный кластер на каждый сервис?**
Нет, кластер один. Все сервисы живут в нём, в namespace `lab`. Группировка по
сервисам происходит на уровне Deployment, а не кластера. В продакшене кластеров
бывает несколько, но делят их по окружениям (разработка, тестирование,
продакшен), а не по сервисам.

**Почему у базы нет blue и green?**
Оба цвета сервиса работают с одной и той же базой - иначе данные, созданные на
blue, не были бы видны после переключения на green. Дублирование базы потребовало
бы репликации и синхронизации, что выходит далеко за рамки стратегии выката
приложения.

**Что такое namespace и зачем он?**
Логический раздел внутри кластера. Даёт три вещи: изоляцию имён, разграничение
прав (наш деплойщик видит только `lab` и ничего не может в `kube-system`) и
возможность удалить всё разом.
