# Шпаргалка для защиты

## Что это за работа, в двух предложениях

Микросервисное приложение из трёх сервисов с полностью автоматизированным
конвейером доставки: от коммита в git до развёрнутой в Kubernetes версии, с
проверками безопасности, тестами, мониторингом и автоматическим откатом.
Прикладная логика намеренно простая - оценивается процесс доставки, а не
бизнес-функциональность.

## Термины

### Общие

| Термин | Определение |
|---|---|
| **CI** (Continuous Integration) | автоматическая проверка каждого изменения кода: линтеры, тесты, сборка |
| **CD** (Continuous Delivery/Deployment) | автоматическое развёртывание проверенного кода в среду исполнения |
| **Пайплайн** | последовательность автоматических шагов; у нас два файла в `.github/workflows/` |
| **Джоб** (job) | одна изолированная задача внутри пайплайна, например «прогнать тесты» |
| **Артефакт** | файл, сохранённый по итогам прогона (у нас - собранная диагностика кластера) |

### Контейнеры

| Термин | Определение |
|---|---|
| **Docker-образ** | неизменяемый шаблон с приложением и его зависимостями |
| **Контейнер** | запущенный экземпляр образа |
| **Dockerfile** | инструкция сборки образа |
| **Multi-stage сборка** | сборка в несколько этапов: инструменты остаются в промежуточном слое, в финальный образ попадает только нужное для запуска |
| **Тег образа** | метка версии; у нас `sha-<коммит>`, чтобы всегда знать, какой код развёрнут |
| **Реестр** (registry) | хранилище образов; у нас GHCR - GitHub Container Registry |

### Kubernetes

| Термин | Определение |
|---|---|
| **Kubernetes (k8s)** | система управления контейнерами: запускает, следит, перезапускает, масштабирует |
| **Кластер** | набор машин под управлением Kubernetes |
| **Под** (Pod) | минимальная единица запуска, один или несколько контейнеров |
| **Deployment** | описание желаемого состояния: какой образ и сколько реплик держать |
| **Service** | стабильный сетевой адрес для группы подов; направляет трафик по **селектору** - набору меток |
| **Namespace** | логический раздел кластера; у нас всё в namespace `lab` |
| **Secret** | объект для хранения паролей и ключей, подключается в под как переменные окружения |
| **Job** | одноразовая задача, которая должна выполниться и завершиться (у нас - миграции) |
| **kubectl** | утилита командной строки для работы с кластером |
| **kind** | Kubernetes IN Docker: настоящий кластер, запущенный внутри docker-контейнеров |
| **probe** | проверка состояния контейнера самим Kubernetes |
| **liveness probe** | «жив ли процесс»; при провале под перезапускается |
| **readiness probe** | «готов ли принимать трафик»; при провале под исключается из Service, но не перезапускается |
| **RBAC** | управление правами: кто и что может делать в кластере |
| **ServiceAccount** | «учётная запись» для программ, а не людей |

### Helm

| Термин | Определение |
|---|---|
| **Helm** | пакетный менеджер для Kubernetes: шаблонизирует манифесты и управляет версиями установки |
| **Чарт** (chart) | пакет с шаблонами манифестов |
| **values** | файл с параметрами, подставляемыми в шаблоны |
| **Релиз** (release) | конкретная установка чарта в кластер, с историей ревизий |
| **Хук** (hook) | действие, привязанное к этапу установки; у нас миграции выполняются хуком `pre-upgrade` |

### Стратегии выката

| Термин | Определение |
|---|---|
| **Blue-green** | две параллельные версии; трафик мгновенно переключается с одной на другую |
| **Canary** | новая версия получает часть трафика, доля постепенно растёт |
| **Rollback** | возврат к предыдущей рабочей версии |
| **Preview Service** | наш дополнительный Service, ведущий на неактивный цвет; нужен, чтобы проверить новую версию до переключения |

### Безопасность

| Термин | Определение |
|---|---|
| **SAST** | статический анализ исходного кода на уязвимости; у нас CodeQL |
| **SCA** | анализ зависимостей на известные уязвимости; у нас npm audit и Trivy |
| **CVE** | запись в публичном каталоге уязвимостей с уникальным номером |
| **gitleaks** | сканер, ищущий пароли и ключи в коде и истории коммитов |
| **Гейт** (gate) | условие, блокирующее продвижение по конвейеру |

### Наблюдаемость

| Термин | Определение |
|---|---|
| **Метрика** | числовой показатель работы системы во времени |
| **Prometheus** | собирает и хранит метрики, опрашивая сервисы по HTTP |
| **Scrape** | сам процесс опроса: Prometheus раз в 10 секунд читает `/metrics` |
| **Grafana** | рисует графики по данным из Prometheus |
| **p95** | значение, ниже которого лежат 95% запросов; показывает задержку без учёта редких выбросов |

### Тесты

| Термин | Определение |
|---|---|
| **Unit** | проверка отдельной функции в изоляции |
| **Integration** | проверка связки компонентов, у нас - код плюс настоящая PostgreSQL |
| **E2E** | проверка всей системы целиком, как её видит пользователь |

## Как устроено приложение

```
браузер
   │ http://localhost:8080
   ▼
web-client (nginx)         ← единственный, кто доступен снаружи
   ├─ /             отдаёт HTML-страницу
   ├─ /api/login  → auth-service   выдаёт JWT
   └─ /api/orders → orders-service проверяет JWT, читает и пишет заказы
                          │
                          ▼
                    PostgreSQL     доступна только внутри кластера
```

**JWT** - подписанный токен. auth-service подписывает его секретным ключом,
orders-service проверяет подпись тем же ключом. Ключ лежит в Kubernetes Secret,
оба сервиса читают его из переменной окружения.

## Как работает конвейер в GitHub

### Что такое workflow

Файл с инструкциями в `.github/workflows/`: при каком событии запускаться и какие
команды выполнить. При наступлении события GitHub берёт **чистую виртуальную
машину** в своём облаке, скачивает на неё код, выполняет шаги и затем машину
уничтожает.

У нас два таких файла - `ci.yml` и `cd.yml`.

### CI и CD - в чём разница

| | CI | CD |
|---|---|---|
| Отвечает на вопрос | «код корректный?» | «система работает после развёртывания?» |
| Что делает | проверяет и собирает образы | разворачивает и проверяет вживую |
| Когда запускается | на каждый push и pull request | после успешного CI на `main`, либо вручную |
| Чем заканчивается | образы лежат в реестре | e2e прошли, кластер уничтожен |

CI заканчивается тем, что образы опубликованы. CD берёт уже готовые образы и
разворачивает их.

### Джобы CI и что они проверяют

| Джоб | Что делает |
|---|---|
| `Lint` | стиль и очевидные ошибки в коде |
| `Unit tests` | отдельные функции в изоляции |
| `Integration tests` | код вместе с настоящей PostgreSQL |
| `SAST (CodeQL)` | ищет уязвимости в **нашем** коде |
| `SCA (npm audit + Trivy)` | ищет уязвимости в **чужих** библиотеках, которые мы подключили |
| `Secret scan (gitleaks)` | ищет пароли и ключи в коде и во всей истории коммитов |
| `Policy checks` | наши собственные правила: нет тега `latest`, `USER` задан числом |
| `Helm` | чарты корректны: `helm lint` плюс рендеринг шаблонов |
| `Build and push` | собирает образы, сканирует их Trivy, публикует в реестр |

Разница SAST и SCA: первый читает код, который написали мы, второй смотрит на
зависимости. Уязвимость чаще приходит именно из зависимостей.

Зачем `Policy checks` отдельно: эти правила не ловятся ни линтером, ни сборкой.
Образ с `USER node` собирается нормально, но под с ним не стартует в Kubernetes -
ошибка видна только в работающем кластере, поэтому вынесена в отдельную проверку.

### Что происходит при Run workflow

1. GitHub выделяет чистую виртуалку
2. Скачивает код из `main`
3. Создаёт **новый kind-кластер** прямо на ней
4. Скачивает образы из реестра по указанному тегу
5. Разворачивает PostgreSQL, Prometheus, Grafana
6. Выкатывает три сервиса через `deploy.sh`
7. Прогоняет e2e
8. Выполняет демонстрацию переключения или отката
9. **Уничтожает виртуалку вместе с кластером**

Кластер каждый раз новый - отсюда и необходимость отдельного шага для показа
переключения: одного релиза в пустом кластере для этого недостаточно.

### Packages в GitHub - это что

Это GHCR, реестр Docker-образов. Три пакета `auth-service`, `orders-service`,
`web-client` создал джоб `Build and push`. Внутри каждого - версии с тегами вида
`sha-42af804`.

Зачем нужен реестр: собранный образ надо где-то хранить, чтобы кластер мог его
скачать.

```
код в git → CI собирает образ → образ в GHCR → CD скачивает и разворачивает
```

Локально образы в реестр не попадают: `kind-up.sh` собирает их и сразу кладёт в
кластер командой `kind load`, минуя реестр.

### Почему развёрнутое в CD нельзя открыть в браузере

Кластер существует только во время прогона, минут пять, на виртуалке внутри
инфраструктуры GitHub. Публичного адреса у неё нет, после окончания прогона нет
ни машины, ни кластера.

**CD доказывает не доступность, а воспроизводимость развёртывания.** Это разные
вещи:

| Вопрос | Кто отвечает |
|---|---|
| Можно ли развернуть систему с нуля на чистой машине? | CD |
| Работает ли она после развёртывания? | e2e внутри CD |
| Можно ли зайти по адресу и потыкать? | локальный кластер |

При этом в CD ничего не имитируется: создаётся настоящий кластер, применяются
настоящие миграции, e2e делают настоящие HTTP-запросы, blue-green реально
переключает трафик. Временная только среда. Аналогия - тест-драйв: машина реально
едет, просто потом её возвращают в салон.

### Зачем CD, если можно развернуть локально

Локальный запуск отвечает «работает у меня». CD отвечает «работает у любого на
чистой машине». Локально всё может работать потому, что полгода назад что-то было
настроено и забыто. CD начинает с пустой виртуалки, где нет ничего.

Плюс CD запускается сам при каждом изменении в `main` - никто не забудет шаг и не
развернёт не ту версию.

## Скрипты: что делает каждый

| Скрипт | Запускается | Что делает |
|---|---|---|
| **`deploy.sh`** | в CD и локально | **основной**. Определяет активный цвет, выкатывает противоположный, гоняет e2e против preview, переключает трафик только при успехе |
| **`rollback.sh`** | вызывается из `deploy.sh` при падении e2e, либо вручную | возвращает трафик на указанный цвет, выключает второй |
| **`run-e2e.sh`** | вызывается из `deploy.sh` и из CD | пробрасывает порты сервисов на localhost и запускает `e2e/run.js` |
| **`kind-up.sh`** | только локально | поднимает весь стек с нуля: кластер, секреты, база, мониторинг, три сервиса |

Важная деталь: `kind-up.sh` **не содержит своей логики выката** - он вызывает тот
же `deploy.sh`, что работает в пайплайне. Поэтому локальная демонстрация и CD
делают одно и то же.

### Как вызываются

```bash
bash infra/scripts/deploy.sh orders-service sha-abc1234
bash infra/scripts/rollback.sh orders-service blue
bash infra/scripts/run-e2e.sh orders-service   # через preview этого сервиса
bash infra/scripts/kind-up.sh
```

## Что делали, по этапам

**A. Репозиторий.** Монорепозиторий с четырьмя каталогами: три сервиса и `infra`.
Каждый сервис самодостаточен: свой Dockerfile, свои тесты, свои зависимости.

**B. CI.** Девять джобов. Восемь проверок идут параллельно, сборка образов
объявляет их все в зависимостях и не стартует, пока хоть одна красная. Образы
сканируются Trivy **до** публикации в реестр.

**C. CD.** Пять Helm-чартов. Три сервиса разворачиваются одним параметризованным
чартом с разными values - чтобы логика blue-green существовала в одном экземпляре,
а не в трёх копиях. Миграции выполняются хуком перед стартом новых подов.

**D. Наблюдаемость.** Сервисы отдают метрики на `/metrics`, Prometheus находит их
по аннотациям подов, Grafana рисует четыре панели. При падении деплоя пайплайн
собирает логи в артефакт.

**E. Безопасность.** Секреты в GitHub Secrets, в кластер попадают как Kubernetes
Secret. gitleaks проверяет всю историю коммитов. Теги `latest` запрещены на двух
уровнях. CD работает под ограниченным ServiceAccount, а не под администратором.

---

## Три уровня отката

| Уровень | Когда срабатывает | Что делает |
|---|---|---|
| 1 | поды новой версии не проходят readiness | Helm сам возвращает релиз (`--atomic`) |
| 2 | e2e упали против preview | селектор не переключается, новая версия выключается |
| 3 | нужно отменить уже переключённый релиз | `rollback.sh` возвращает селектор назад |

**Второй уровень главный.** Проверка идёт до переключения трафика, поэтому
пользователи не видят сломанную версию ни секунды.

**6б. Запросы в Prometheus - опционально, если попросят показать сырые данные.**

Открыть http://localhost:9090/graph и вставить один из трёх:

```
up
```
Самый простой. Возвращает 1 для каждого пода, который ответил на опрос, и 0 для
недоступного. **Ожидаемо увидеть:** четыре строки со значением 1 - по два пода
auth-service и orders-service. Доказывает, что сбор метрик реально идёт.

```
sum(up) by (service, color)
```
Те же поды, сгруппированные по сервису и цвету. **Ожидаемо увидеть:**
`{service="orders-service", color="blue"} 2`. Это ровно тот запрос, что питает
панель blue-green: в момент переключения появляется вторая строка с другим
цветом.

```
sum(rate(http_requests_total[1m])) by (service)
```
Скорость запросов за последнюю минуту. **Ожидаемо увидеть:** ненулевые значения,
если только что кликал в приложении, и близкие к нулю, если система простаивала.
Счётчик `http_requests_total` только растёт, поэтому интересна не его величина, а
скорость роста - её и даёт `rate`.

Если хочется показать всю цепочку от сырых данных к графику, порядок такой:
`/metrics` одного сервиса (текст с числами) → `/targets` (кого Prometheus нашёл)
→ Grafana (что из этого получилось).

## Вероятные вопросы

**Почему blue-green, а не canary?**
Задание разрешает любую из двух. Blue-green переключает трафик атомарно, поэтому
не бывает состояния, когда часть пользователей на сломанной версии. Плюс откат -
это возврат одного поля селектора.

**Почему кластер kind, а не облако?**
Задание требует развёртывание в Kubernetes, не уточняя, какой. kind - настоящий
Kubernetes, просто запущенный в контейнерах. Один и тот же скрипт работает и в
пайплайне, и локально.

**Почему в CD каждый раз новый кластер?**
Так проверяется весь путь с нуля, включая создание namespace, секретов и
миграций. Побочный эффект: демонстрация переключения требует второго релиза
внутри того же прогона, для этого есть отдельный шаг.

**Почему один чарт на три сервиса?**
Логика blue-green одинакова для всех. В трёх копиях она неизбежно разошлась бы
при первой правке. Различия вынесены в три файла values.

**Зачем preview Service?**
Чтобы прогнать e2e против новой версии до того, как она получит пользовательский
трафик. Без него проверка шла бы уже после переключения, то есть на пользователях.

**Почему красный прогон - это доказательство?**
Зелёный пайплайн не доказывает, что защита срабатывает: возможно, она просто ни
разу не понадобилась. Красный показывает механизм в действии.

**Как секреты попадают в приложение?**
GitHub Secrets → шаг пайплайна создаёт Kubernetes Secret → под получает значения
через `secretKeyRef`. В коде и чартах их нет, gitleaks проверяет это на каждом
коммите.

**Почему запрещён тег latest?**
По `latest` невозможно понять, какой код работает в кластере, и откат становится
неоднозначным. У нас тег равен хешу коммита. Запрет реализован и в чарте, и в CI.

**Что будет, если упадёт база?**
Readiness probe у orders-service делает запрос к базе. Под перестанет считаться
готовым и будет исключён из балансировки, но не перезапустится - перезапуск не
чинит недоступную базу.

**Чем отличаются liveness и readiness?**
Liveness отвечает на вопрос «жив ли процесс» и приводит к перезапуску. Readiness -
«готов ли обслуживать» и управляет тем, идёт ли на под трафик. На readiness
построен механизм выката: пока новые поды не готовы, релиз не считается успешным.
